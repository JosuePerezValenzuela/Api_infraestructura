# Design: Redis Cache — Bloque

## Technical Approach

Mechanical extension of the proven catalog caching pattern (campus, tipo-ambiente, tipo-bloque, facultad). Layer `CacheService.getOrSet` on `ListBloquesUseCase` and `CacheService.invalidateNamespace` on create, update, delete. No new infrastructure — reuses `CacheService`, `CacheKeyBuilder`, `CACHE_TTL` env var.

Bloque differs: list uses `page/limit` with 10+ filter fields (`search`, `orderBy`, `orderDir`, `facultadId`, `campusId`, `tipoBloqueId`, `activo`, `pisosMin`, `pisosMax`). Write cases have complex validation but invalidation follows the same namespace-clearing approach.

## Architecture Decisions

| Decision | Choice | Alternatives | Rationale |
|----------|--------|-------------|-----------|
| Cache strategy | Cache-aside (`getOrSet`) | Write-through, cache-through | Proven in 4 prior catalog modules; wraps repo call transparently |
| Invalidation scope | `invalidateNamespace('bloque:*')` | Per-key eviction | Single wildcard covers all param variations; simpler than tracking individual keys |
| Invalidation timing | After repo write, before return | Before write, in a hook | Ensures cache only cleared after successful write; failed writes don't invalidate |
| Update invalidation point | After update + optional cascade block | Inside each branch | Single call after both operations; cascade happens before invalidation |
| TTL source | `CACHE_TTL` env var (default 300s) | Hardcoded, per-module TTL | Consistent across all catalog modules; already configured |
| Key naming | `page=` / `limit=` (bloque convention) | `take=` (campus/facultad convention) | Uses bloque's existing `ListBloquesOptions` shape with `limit` param name |

## Architecture

```
                    BloqueModule
  ListBloques ──getOrSet──┐
  CreateBloque ──invalidate│
  UpdateBloque ──invalidate├── CacheService
  DeleteBloque ──invalidate│
              providers────┘
```

## Data Flow

### Read (list)

```
execute({ page, limit, search, orderBy, orderDir, facultadId, campusId,
          tipoBloqueId, activo, pisosMin, pisosMax })
  → defaults (page=1, limit=6, orderBy='nombre', orderDir='asc')
    → CacheKeyBuilder.list('bloque', { page, limit, search, orderBy, orderDir,
                                       facultadId, campusId, tipoBloqueId,
                                       activo, pisosMin, pisosMax })
      → cacheService.getOrSet(key, ttl, () => repo.list(options))
        → returns { items, meta }
```

Different filter combos produce distinct keys. TTL from `config.get('CACHE_TTL', 300)`.

### Write (create/update/delete)

```
validate → repo.write(payload) → [update+cascade? → markBloquesCascadeInactive]
  → invalidateNamespace('bloque:*') → return
```

Invalidation runs after repo ops succeed. If the repo throws, cache is NOT invalidated.

## Cache Key Format

Generated by `CacheKeyBuilder.list('bloque', params)` — params sorted alphabetically, null/undefined excluded. Uses `limit` (bloque convention), not `take`.

```
bloque:list:activo=true&campusId=3&facultadId=5&limit=6&orderBy=nombre&orderDir=asc&page=1&pisosMin=2&search=A
bloque:list:activo=true&campusId=3&facultadId=5&limit=6&orderBy=nombre&orderDir=asc&page=2&pisosMin=2&search=A
bloque:list:page=1&limit=6
bloque:list:orderBy=pisos&orderDir=desc&page=1&limit=6&pisosMax=5
```

## Invalidation

`invalidateNamespace('bloque:*')` — SCAN + DEL matching keys. Single wildcard covers all list param variations.

## Interfaces / Contracts

No new interfaces. Existing contracts remain unchanged:

- `CacheService.getOrSet<T>(key, ttl, factory)` — wraps factory with cache-aside
- `CacheService.invalidateNamespace(pattern)` — SCAN + DEL by wildcard
- `CacheKeyBuilder.list(resource, params)` — deterministic key generation
- `ConfigService.get('CACHE_TTL', 300)` — TTL from env

All use cases return the same shapes they do today — caching is transparent to callers.

## Testing Strategy

| Layer | What to Test | Approach |
|-------|-------------|----------|
| Unit | List — cache hit returns cached data without calling repo | Mock `cacheService.getOrSet` to return cached value; verify `repo.list` NOT called |
| Unit | List — cache miss calls repo and caches result | Mock `getOrSet` to invoke factory; verify `repo.list` IS called |
| Unit | List — Redis error falls through to DB | Mock `getOrSet` to throw then invoke factory; verify response comes from repo |
| Unit | Create — invalidation called after successful create | Mock `cacheService.invalidateNamespace`; verify called with `'bloque:*'` |
| Unit | Update — invalidation called after successful update + cascade | Same mock/verify pattern |
| Unit | Delete — invalidation called after successful delete | Verify `invalidateNamespace` called with `'bloque:*'` after `repo.delete()` |
| Unit | Write use cases — invalidation NOT called on error | Force repo to throw; verify `invalidateNamespace` NOT called |

## Migration / Rollout

No migration required. No schema changes, no config changes — `CACHE_TTL` is already deployed. Pure code change hot-deployable via standard PR.
